# AI沙盒项目

## 一.初版设计
AI沙盒的初版最小可实现版本，它的逻辑极其简单。

首先，考虑一个问题，对于一个世界来讲，需要什么？

### 1.世界的组成

**时间和空间**

这是一切存在的基础。

**实体**

世界中可以活动的最小单位。人类，物品，他们都有着自己的属性，就像类一样。

**规则**

决定了人们的行为，决定了实体的状态如何变化。

**事件**

所有实体活动的总和，我们可以将所有执行过的决策，都视为事件，统一管理。

**记忆**

一份相关事件的集合，这个集合独属于所有设定上有能动性的实体。

**决策**

所有有能动性的实体，基于当前状态和记忆，可以做出的行为。

### 2.实现细节
对于最小可实现产品MVP，我只是实现了上面的几个方面。

时间、空间、实体、决策。

**实体：**

助手类 Agent 和助手快照类 AgentState，前者封装了助手相关的静态属性，如ID、姓名和AgentState；后者封装了助手相关的动态属性，如当前的位置（x，y）。

**空间和时间：**

世界类 Wolrd 和世界快照类 WorldState，前者封装了世界相关的静态属性，如世界的尺寸和Agents列表；后者封装了世界相关的动态属性，如世界当前的时钟和AgentStates列表。

**决策：**

最开始的实现，想法很简单，把助手和世界一起扔给LLM，让LLM返回JSON格式的、具体的行动决策。

最后再根据行动决策来更新Agent和World的状态。

对于MVP版本来说，可扩展性极差，实现的行动决策也只有一个——移动。

### 3.执行流程
外部HTTP触发走一步（step by step）-> 显式调用 stepForward()，时钟+1 

-> 用 同一张世界快照 ，朴素串行遍历让每个Agent问LLM拿决策，并执行行动（仅MoveAction）

-> 返回HTTP响应。

整个流程，就是一个 感知-决策-执行 的循环。

### 1.事件系统（Event system）
Bus，也就是总线，是个很神奇的设计。

我在计算机组成原理中第一次了解时，感觉这是个看起来很简单，但极其天才的想法。

因此，在vab2.0中，我优先选择了这个架构来对这个项目进行优化。

#### 1.1 MVP版本的问题
初版中，所有的动作执行是**一次性的、无记录的**：

- Agent移动了，除了状态更新，**没有留下任何历史痕迹**

- 无法回溯"谁在什么时候做了什么"

- 决策理由（reason）用完即弃，无法用于后续分析

- 系统无法审计、无法回放

#### 1.2 vab2.0的设计思路
一句话总结：将**所有实体活动的总和"抽象为事件（Event），统一管理**。

事件是世界运行的**唯一事实来源**，是连接"决策->执行->记忆"的中间层。

也就是说，多Agent间，不能直接通信，而是通过总线进行通信。

```
决策输出 -> 生成事件 -> 事件持久化 -> 记忆系统订阅 -> 后续决策参考
```

### 1.3 核心组成

| 组件 | 职责 | 说明 |
|------|------|------|
| **Event（事件基类）** | 定义事件的通用元数据 | id, tick, timestamp, priority, sourceSystem, processed —— 所有事件都必须包含的6个维度 |
| **Event类型体系** | 区分不同性质的事件 | `MoveEvent`（移动）、`TickEvent`（时间步完成）、后续可扩展`TalkEvent`（对话）、`PickupEvent`（拾取）等 |
| **EventBus（事件总线）** | 事件路由中心，支持多种事件类型的订阅和发布 | 维护订阅者索引，维护全局订阅者列表，维护内部的临时事件历史列表 |
| **EventListener（事件监听接口）** | 事件监听者接口 | 所有想要处理事件的组件都要实现这个接口 |

### 2.扩展记忆系统（Extended Memory）

#### 2.1 MVP版本的问题
初版中，Agent的决策是**完全无状态**的：

- 每次决策没有之前的记忆，只是单轮决策。

- 本质上是一个**马尔可夫决策**，每一步独立同分布，没有智能体的"自我连续性"

#### 2.2 vab2.0的设计思路
引入**分层记忆架构**，将"一份相关事件的集合"从概念变为工程实现。

何为分层呢？

简单说就是将记忆分为短期记忆，工作记忆，长期记忆。

记忆不是事件的简单堆积，而是经过**筛选、摘要、结构化**的可用上下文。

上述都是Agent的描述，但实际上，我发现，它只实现了基于内存的短期记忆。

#### 2.3 三层记忆模型

下面的三层模型仅供参考。

只有短期记忆真正的是实现了。

由短期转移到工作记忆和长期记忆的部分，没有实现。
```
┌─────────────────────────────────────────────────┐
│  长期记忆（Long-term Memory）                    │
│  • Agent的核心性格、自我认知、长期目标            │
│  • 由LLM定期从短期记忆中蒸馏总结                  │
│  • 变化频率低，每N个tick更新一次                   │
├─────────────────────────────────────────────────┤
│  工作记忆（Working Memory）                      │
│  • 最近K个tick的事件序列（原始事件级）            │
│  • 当前可感知的环境状态                           │
│  • 正在进行中的意图/计划                          │
│  • 直接注入到每一次LLM决策的Prompt中              │
├─────────────────────────────────────────────────┤
│  短期记忆（Short-term Memory）                   │
│  • 最近的M个决策+执行事件                         │
│  • 与其他Agent的互动记录                         │
│  • 保留原始事件粒度，可被上层检索                 │
└─────────────────────────────────────────────────┘
```

#### 2.4 记忆接口和类
设计了一个顶层记忆接口 MemoryStore，所有记忆存储（Redis、MySQL等）相关的类都要实现这个接口。

这个记忆接口提供了增删改查四种类型的方法。

设计了一个记忆管理类 AgentMemory，在整个项目中通过组合，作为 Agent 的一部分。

设计了一个记忆类 MemoryEntry，作为记忆系统的最小存储单位，封装了一条记忆应该包含的字段，ID、type、agentId等。

### 3.多Agent编排（Multi-Agent Orchestration）

#### 3.1 MVP版本的问题
初版中，Agent的调度是**朴素的串行遍历**：
```java
for (Agent agent : agents) {
    决策 -> 执行
}
```
存在的问题：
- **执行顺序有隐含的先后优势**：第一个决策的Agent看到的是"旧世界"，最后一个看到的是"已经被前面的人改了一半的世界"

- **没有调度策略**：所有Agent同等优先级，无法区分"紧急/重要"

- **没有并发能力**：串行执行是性能瓶颈（1000个Agent就要1000次LLM调用串起来）

- **无法处理Agent间的依赖**：如果A的决策依赖B的动作结果，串行模型会出错

#### 3.2 vab2.0的设计思路
引入Orchestrator（编排器）作为调度层，将"遍历Agent"从TickSchedule中解耦出来，形成独立的调度体系。编排器的核心职责是：**在正确的时间，用正确的策略，让正确的Agent做出决策**。

但实际上，根本就没有实现！！！

Agent把我的代码结构变了，它将部分代码块抽成方法，加入像模像样的注释，但是本质没变。

还是串行模型，功能一点没变。

所以这部分就算是vab2.0的一个缺陷吧，留在后面改进。
