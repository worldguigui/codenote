# 选课评价平台项目优化

这个项目来源于一个念头，一个在选课时自然而然萌发的念头：这个课的考核形式？严格考勤吗？给分高不高？

在这上面纠结的人肯定不止我一个，正好那段时间，自己学习了一部分的Java相关的后端技术栈，不如就做一个网站吧？上面有着课程，还有学生对其的评价。

差不多两个月，第一版就做出来了，后端、前端、网站部署，做得相当粗糙。

## 一.IP限流
旧有项目中：没有限流的功能。

潜在的隐患：用户可以无限次地尝试，暴力破解密码或频繁请求服务，占用服务器资源。

解决方案：基于Redis的令牌桶算法。

Spring中有一个HttpServletRequest类，它封装了客户端向服务器发送的HTTP请求的所有数据。

在登录接口中，我们可以获取这个类的对象，获取客户端的IP。

通过Redis缓存这个IP，和它的访问次数，这样就可以实现限流的功能。

具体如何缓存呢？这里我使用令牌桶算法。

该算法有三个关键参数。

容量（Capacity），表示桶最多能放多少个令牌。

填充速率（Rate），每秒/分钟填充多少个令牌。

当前令牌数（Tokens，桶里现在有多少个令牌。

每次请求，如果桶中还有令牌，则允许访问；否则禁止访问。

具体实现呢，就是用Redis缓存，以IP作为key，以{Tokens,timestamp}作为value。

当一个请求到达时，先查Redis，有则读取，判断桶中是否有空余的令牌，并根据timestamp更新缓存。

如果Redis中没有，则读取默认的桶配置，并写入缓存。

## 二.登录优化
旧有项目中：用户登录输入的密码使用MD5加密，将加密后的密码存进数据库。

潜在的隐患：安全性较低，存在暴力破解的可能。虽然在登录时有IP限流的措施，但无法从根本上解决暴力破解的问题。

解决方案：使用Spring Security 框架提供的 BCryptPasswordEncoder。

BCrypt 会自动为每个密码生成一个盐值，并且将盐和最终的哈希值拼接在一起存入数据库。

“盐”（Salt）是一个随机生成的、独一无二的字符串，将其与用户的明文密码拼接在一起，然后再对这个新的字符串进行 MD5（或其他哈希）运算，得到最终的加密密码。

```
$2a$10$WkAYB/aJshwjJNnPwK.cBenGyiXgkxCU3Ew9ff2PMIsjAbwc8JQJK
```

这是一个实际的存储在数据库的加密密码。

`2a` 是算法标识，表示使用的BCrypt算法版本。

`10` 是成本因子，表示进行了 2的10次方=1024 次哈希迭代。这个参数人为控制了哈希计算的时间，增加了暴力破解的时间成本。

`WkAYB/aJshwjJNnPwK.cBe` 是随机生成的22位盐值。

`nGyiXgkxCU3Ew9ff2PMIsjAbwc8JQJK` 是最终生成的31位加密密码。

## 三.推荐优化
旧有项目中：没有推荐算法，我采取的是根据评论人数降序排序，推荐排名靠前的课程。

潜在的隐患：没有推荐算法。

解决方案：采取基于课程的协同过滤算法，通过余弦相似度和Jarcard系数进行置信度加权。

为了实现推荐功能，给课程添加了一个字段，评分，rating，1分最差，5分最好。

基于这个评分字段，创建一个方法 rebuildSimilarityMatrix()。

下面简单讲一下这个方法的整体流程：

```
1.获取所有评分(关键字段：userId, lessonId, rating)

2.建表lessonRatingMap，表结构如下：lessonId:<userId,rating>。

此时，我们得到了一个关于课程的评分矩阵，userId可以类比于矩阵的维度。

3.遍历，两两匹配，计算余弦相似度和Jarcard系数，相乘得到推荐系数。

余弦相似度衡量了两个课程的选择相似程度，取值-1到1，越接近1，证明评分模式越接近，可以相互推荐。

Jarcard系数衡量的是两个课程共同评分用户的占比，一定程度上拉低少量样本导致的虚高问题。防止了冷门课程靠少量高评分欺骗推荐系统，让推荐结果更鲁棒。

4.存入Redis。

数据格式：lesson:sim:matrix:<6:37,0.210>，6和37是lessonId，0.210是它们的推荐系数。

```

可以看到，在流程中，涉及到的计算达到了大O平方的时间复杂度，实时运算的话，延迟极高。

因此，我选择离线计算，采取 SpringTask 定时任务，在凌晨三点这样一个访问量极少的时间段，根据评分数据，构建相似度矩阵。

rebuildSimilarityMatrix() 方法只构建了相似度矩阵，为用户实时推荐的逻辑在 recommendLessonsByUser()方法中。

下面简单讲一下这个方法的整体流程：

```
1.根据 userId 获取该用户所有评过分的课程列表 lessonIds

2.如果用户没有发表过任何评论，则给他推荐热门课程。

热门课程排行榜以平均分作为排序指标，如果平均分相等，则比较评论数。

3.如果用户有发表过任何评论，进行课程推荐部分的逻辑。建表buildUserRatingMap，表结构如下：<lessonId, rating>

4.根据 lessonId，从Redis的相似度矩阵(lesson:sim:matrix)中获取所有与其相关的数据，并建表 Map<Long, Double> similarLessons。

如：lessonId 为 37，我们要得到 <6:37,0.210>、<37,210,0.6>、<37,0,0.37>等，提取为 similarLessons，<6,0.210>、<210,0.6>、<0,0.37>等。

5.到此为止，我们得到了 lessonId 和与它相关的 similarLesson。

对于每个 lessonId，根据 similarLesson 中的相似度，对所有未选择的课程（推荐内容由具体的代码逻辑决定，也可以推荐用户选择过的课程）进行加权处理。

6.建表，recommendationScores <Long,Double>，以推荐课程id作为主键，累加所有 similarity * rating，得到推荐分数。最后根据推荐分数降序排列。

如果推荐课程不足，则以热门课程作为补充。

```
步骤2和3都可以加入缓存优化。2中加入热门课程的缓存，用lesson:hot:rank作为主键；3中加入推荐课程的缓存，recommand:user:limit作为主键。

推荐课程的缓存在用户提交新的评分后会删除，等待下一次计算出新的推荐课程。

至此，推荐系统的优化就结束了。

## 四.缓存优化
旧有项目中：没有缓存优化。

潜在的隐患：访问量稍微增加，接口响应速度会变慢。

解决方案：增加Redis缓存逻辑。

在面试八股里面，Redis部分有一个叫做双写一致性的问题——当数据库和缓存都需要更新时，如何保证两者最终状态一致。

大概讲的是，用户从缓存读数据，如果数据库发生变更，此时Redis中的数据就是过时的了，再继续从缓存读数据，就不对了。

这通常发生在数据库频繁变更的场景，比如说商品库存、个人余额，但在这个项目里，课程详情等对于时效性要求并不严格，并不会由于十几条评分更新不及时，导致推荐系统失效。

在项目中，使用Redis缓存热点课程数据，采用Cache Aside模式，更新数据库后删除缓存。

课程详情、推荐课程、热门课程、相似度矩阵，都有缓存优化，在选择读取时，都会优先考虑从缓存中读取，没有，再执行对应的逻辑计算得到推荐课程和热门课程，并加到缓存中。
